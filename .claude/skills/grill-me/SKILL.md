# grill-me — ตรวจแผนแบบซักถามทีละข้อ

เป้าหมาย: ทำให้ผู้ใช้กับ Claude เข้าใจแผนตรงกันและแผนแข็งแรงพอจะใช้งานจริง โดยการซักถามอย่างตรงไปตรงมา ไม่ใช่การชม

หัวข้อที่ผู้ใช้ส่งมา: $ARGUMENTS
(ถ้าว่าง ให้ตรวจทั้งโปรเจกต์ในรีโพนี้)

## ขั้นที่ 0 — อ่านก่อนถาม

ก่อนถามข้อแรก ให้อ่านไฟล์ที่เกี่ยวข้องจริงในรีโพ (เช่น `index.html`, `README_TH.md`, `WORKSHEET_TH.md`) อย่าถามสิ่งที่ตอบได้จากโค้ดเอง
สร้างรายการช่องโหว่ที่เป็นไปได้ไว้ภายใน แล้วเรียงลำดับตามผลกระทบ (ร้ายแรงที่สุดก่อน) ห้ามแสดงรายการทั้งหมดในครั้งเดียว

## กติกาการซักถาม (ต้องทำตามทุกข้อ)

1. **ถามครั้งละ 1 ข้อเท่านั้น** แล้วจบข้อความ รอผู้ใช้ตอบ ห้ามถามหลายข้อรวดเดียว
2. แต่ละคำถามต้องมี:
   - **หลักฐาน**: อ้างไฟล์และบรรทัด (`path:line`) หรือสถานการณ์จริงที่ทำให้เกิดปัญหา
   - **คำถาม**: เจาะจง ตอบได้ ไม่กำกวม
   - **คำแนะนำของ Claude**: คำตอบที่แนะนำพร้อมเหตุผลสั้น ๆ และทางเลือกอื่นถ้ามี
3. เมื่อผู้ใช้ตอบ ให้:
   - ประเมินคำตอบ: ปิดช่องโหว่ได้จริงไหม มีกรณีไหนที่ยังหลุด
   - ถ้าคำตอบยังมีช่องโหว่ ให้ชี้ออกมาและถามต่อในประเด็นเดิม (ยังไม่ข้ามไปข้อใหม่)
   - ถ้าคำตอบดีพอ ให้สรุปข้อตกลงใน 1–2 บรรทัด แล้วจึงถามข้อถัดไป
4. ห้ามแก้ไขไฟล์ใด ๆ ระหว่างการซักถาม เว้นแต่ผู้ใช้สั่งให้แก้อย่างชัดเจน
5. ถ้าผู้ใช้ตอบว่า "ข้าม" ให้บันทึกว่าเป็นความเสี่ยงที่ยอมรับแล้วไปข้อถัดไป ถ้าตอบว่า "พอ" หรือ "จบ" ให้ไปขั้นสรุปทันที
6. ใช้ภาษาเดียวกับผู้ใช้ (ไทยเป็นค่าเริ่มต้นสำหรับโปรเจกต์นี้) และพูดตรง ๆ ไม่อ้อมค้อม

## รายการตรวจสำหรับโปรเจกต์ AR Motor Status

ใช้เป็นแหล่งคำถาม ให้ตรวจกับโค้ดจริงก่อนทุกครั้ง เพราะโค้ดอาจเปลี่ยนไปแล้ว

**A-Frame / โค้ดในหน้าเว็บ**
- ค่าที่ใบงานให้ผู้เรียนแก้ใน HTML (สีมอเตอร์, ชื่อเครื่องจักร) ถูก JavaScript เขียนทับด้วยค่าคงที่หรือไม่ เมื่อกดปุ่มสลับสถานะ
- คอมโพเนนต์ `spin-control` และการสลับ `active` ทำงานถูกต้องหลังเปลี่ยนค่า `speed`
- ข้อความ `a-text` อ่านออกจากมุมที่ผู้เรียนถือมือถือจริงหรือไม่ (rotation, width, side)
- เวอร์ชัน A-Frame กับ AR.js เข้ากันได้และถูก pin ไว้

**AR.js / Hiro Marker**
- แหล่งโหลดสคริปต์ AR.js (เช่น `raw.githack.com`) เชื่อถือได้ไหมเมื่อมือถือทั้งห้องโหลดพร้อมกัน ควรใช้ CDN ที่มีเวอร์ชันแน่นอน (เช่น jsDelivr) หรือเก็บไฟล์ไว้ในรีโพ
- ขนาด แสง ระยะ และวิธีแสดง Marker (พิมพ์ vs. แสดงบนจออีกเครื่อง) ระบุชัดเจนพอหรือไม่
- ข้อความเมื่อ `markerFound` / `markerLost` ช่วยผู้เรียนแก้ปัญหาได้จริงหรือไม่

**GitHub Pages / การใช้งานในห้องเรียน**
- ขั้นตอนตั้งค่า Pages ตรงกับหน้าจอ GitHub ปัจจุบัน (เช่น `/ (root)`) และเว็บใช้ HTTPS เพื่อให้เปิดกล้องได้
- ผู้เรียนแต่ละคนแก้โค้ดแล้วทดสอบบนมือถือของตัวเองอย่างไร (fork แยก? รอ Pages build นานเท่าไร? ปัญหา cache?)
- แผนสำรองเมื่อไม่มีอินเทอร์เน็ต Wi-Fi ช้า หรือมือถือไม่รองรับ (iOS Safari, เบราว์เซอร์ในแอป LINE/Facebook)
- กล้องไม่ได้รับอนุญาต: ผู้สอนมีวิธีแก้ที่ทำได้ภายในเวลาเรียน 45–60 นาทีไหม

**การเรียนรู้และการประเมิน**
- ผลลัพธ์การเรียนรู้ใน README ตรงกับงานในใบงานครบทุกข้อหรือไม่
- เกณฑ์ว่าผู้เรียน "ทำสำเร็จ" คืออะไร ผู้สอนตรวจอย่างไร
- เวลาที่ใช้จริงต่อขั้น (ตั้งค่า GitHub มักกินเวลาที่สุด) สมเหตุสมผลหรือไม่

## ขั้นสรุป

เมื่อหมดคำถามสำคัญหรือผู้ใช้ขอจบ ให้สรุปเป็น:

1. **ข้อตกลงที่ได้** — แต่ละข้อ 1 บรรทัด
2. **ความเสี่ยงที่ยอมรับ/ข้ามไป**
3. **สิ่งที่ต้องแก้ไข** — เรียงตามความสำคัญ พร้อมไฟล์ที่เกี่ยวข้อง

แล้วถามผู้ใช้ว่าต้องการให้ลงมือแก้ข้อใดหรือไม่ ห้ามแก้เองโดยไม่ได้รับอนุญาต
